# /exp-pilot-run

> Выполнение пилотного эксперимента, описанного в YAML-файле спецификации пилота.
> Читает спецификацию из `experiments/pilot/{slug}.yaml`, пишет пилотный код, запускает эксперимент (подтверждение от пользователя перед операцией и требование ручной проверки заявителем), и возвращает сырые результаты вызывающему.
> **Независимо от режима работы, перед подготовкой экспериментальных кодов и их развёртыванием для эксплуатации необходимо получить подтверждение от пользователей. Пользователи должны вручную проверить соответствующую информацию, включая коды и экспериментальные конфигурации (такие как пути к наборам данных, выбор параметров интерфейса, конфигурацию API и т.д.). Эксплуатация может быть запущена только после подтверждения; в противном случае вносятся исправления до получения согласия пользователей на выполнение.**
> Поддерживает **local** (прямой GPU) и **remote** (SSH-развёртывание через `tools/remote.py`) режимы.
> НЕ изменяет какие-либо wiki-страницы. НЕ оценивает проход/провал — результаты оцениваются через `/exp-pilot-eval`.

## Входы

- `idea-slug`: slug для поиска `experiments/pilot/{slug}.yaml`
- `--env local|remote` (опционально, по умолчанию `local`): среда развёртывания
  - `local`: запуск напрямую на локальном GPU
  - `remote`: развёртывание на удалённой машине через SSH (требуется `config/server.yaml`)

## Выходы

- Пилотный код: `experiments/pilot/code/{slug}/` (train.py, config.yaml, run.sh, requirements.txt)
- Пилотные результаты: `experiments/pilot/code/{slug}/results/seed_{N}.json`
- Лог пилота: `experiments/pilot/code/{slug}/pilot.log`
- **PILOT_REPORT** (выводится в терминал) — таблица результатов, детали запуска, аномалии
- Возврат сырых результатов и ключевых метрик вызывающему
- НЕТ модификаций wiki-страниц

## Взаимодействие с Wiki

  - `experiments/pilot/code/{slug}/run.sh` — скрипт запуска

## Рабочий процесс

**Предусловия**: Убедитесь, что рабочая директория — корень проекта wiki (директория, содержащая `wiki/`, `raw/`, `tools/`).

---

**Этап 1: Подготовка**

1. **Чтение спецификации пилота**:
   **Если спецификация пилота для выбранной идеи не существует в соответствующем месте, напомните пользователю и создайте её, следуя шагам создания спецификации пилота в /ideate Этап 5.**
   - Загрузите `experiments/pilot/{slug}.yaml`
   - YAML имеет корневой ключ `pilot_spec:`; все поля ниже вложены под ним
   - Проверьте наличие обязательных полей в `pilot_spec:`: `implementation`, `setup`, `metrics`, `baseline`, `success_criterion`
   - Извлеките из `pilot_spec:`: repo, entry_point, modifications, files_to_create, setup (model, dataset, hardware, framework, batch_size, max_steps, learning_rate, seeds, other_hparams), metrics, baseline, success_criterion, hypothesis, approach_sketch

2. **Загрузка контекста реализации**:
   - Используйте `pilot_spec.hypothesis` и `pilot_spec.approach_sketch` как основное руководство по реализации (страницы идеи написаны `/ideate` Этап 4, до пилота)
   - Прочитайте описания методов связанных статей для деталей алгоритма (из `wiki/papers/` если они есть)
   - Прочитайте репозиторий исходной статьи для базового кода

3. **Проверка набора данных и других конфигураций**
   - Набор данных указан в разделе setup спецификации пилота.
   - Получите путь к набору данных (выберите локальный или удалённый доступ в зависимости от параметра --env). Вы можете запросить у пользователя локальный или удалённый путь к набору данных и выполнить автоматическое извлечение самостоятельно.
   - Если набор данных отсутствует, предложите пользователю, уточните необходимость скачивания набора данных и подтвердите путь установки и источники скачивания с пользователем.
   - Проверьте целостность и доступность набора данных и систематизируйте прилагаемые спецификации структуры и инструкции по использованию набора данных.
   - Другие конфигурации включают: имя вызываемой модели LLM, URL, API-ключ и другую 관련ую информацию.

4. **Написание пилотного кода** в `experiments/pilot/code/{slug}/`:

**Принцип модульного программирования: избегайте помещения большого объёма кода в один файл, если проект небольшой и простой по логике**

>Напоминание о цели пилотного эксперимента: цель — **обнаружить явные провалы** (расхождение, сильная деградация, фундаментальная несовместимость), **а НЕ измерить конечную производительность**. Следуйте уменьшенной конфигурации спецификации пилота: размер батча = 1/4–1/8 от статьи, шаги обучения = 10–30% от полных. Это для оценки ценности реализации идеи в определённой степени при меньших затратах, всегда включая сравнение с базовым методом. Не пытайтесь оптимизировать для оптимальных результатов — пилотный эксперимент должен лишь подтвердить "отсутствие явного коллапса". С общей производительностью на ранних и средних этапах результаты, улучшенные, примерно на уровне или немного хуже базового — все приемлемы.

Возможные справочные пути для кода пилотного эксперимента:
   - Путь А: Обратитесь к репозиторию оригинальной методической статьи и измените код на основе этого репозитория для получения кода пилотного эксперимента.
   - Путь Б: Реализуйте интегрированную версию на основе идеи органического слияния (например, проверьте, достигает ли производительность и стоимость баланса).
   - Путь В: Обнаружьте типичные слепые зоны, сломайте существующие предположения на основе новых настроек и проверьте, не работают ли все существующие методы в новых настройках.

   - `train.py`: скрипт обучения/оценки на основе конфигурации setup спецификации пилота, включая:
     - Разбор аргументов (argparse, все гиперпараметры из спецификации конфигурируемы)
     - Загрузка данных (поддержка `setup.dataset` из спецификации)
     - Инициализация модели (поддержка `setup.model` и базовой модели из спецификации)
     - Цикл обучения/вывода (с учётом `setup.max_steps` для сокращённого обучения)
     - Вычисление метрик (соответствие списку `metrics` из спецификации)
     - Сохранение результатов (формат JSON, путь: `experiments/pilot/code/{slug}/results/seed_{N}.json`)
     - Управление случайным сидом
   - Другие необходимые папки и файлы кода, такие как utils, tools (например, `utils.py`, `data_loader.py`)
   - `config.yaml`: все гиперпараметры из спецификации (learning_rate, batch_size, max_steps и т.д.)
   - `run.sh`: обёртка запуска (включает CUDA_VISIBLE_DEVICES, логирование, активацию conda)
   - `requirements.txt`: зависимости (если отличаются от основного проекта)

5. **Проверка работоспособности** (валидация в малом масштабе):
   - Запуск в минимальном масштабе (10 шагов / небольшое подмножество)
   - Проверка: нет падений кода, данные загружаются корректно, GPU доступен, loss конечен
   - Если проверка не прошла → исправьте код, повторите один раз; если всё ещё не работает, сообщите об ошибке и остановитесь


**Контрольная точка: ручная проверка пользователями**

> **Примечание**: Перед подготовкой экспериментальных кодов для развёртывания и эксплуатации подтвердите с пользователями и запросите ручную проверку соответствующей информации, включая коды и экспериментальные конфигурации. Продолжайте только после подтверждения; в противном случае вносите исправления до получения согласия пользователей на выполнение.


**Этап 2: Запуск**

> **Напоминание о цели пилота**: Это **короткий, диагностический запуск** — не полный эксперимент. Запуск должен завершиться быстро (сокращённые шаги). Если он расходится или зависает за 2× ожидаемого времени, это само по себе полезный сигнал. Сообщите об этом; не пытайтесь спасательные запуски.

#### Локальный режим (`--env local` или по умолчанию)

1. **Проверка GPU**: `nvidia-smi` для подтверждения доступности GPU и достаточного объёма VRAM. Если `setup.hardware` — `cpu`/`none`/пусто и сгенерированный код не содержит ключевых слов CUDA/GPU, пропустите проверку GPU и перейдите к шагу 2.
2. **Оценка времени выполнения**: на основе `setup.hardware` (модель GPU), `setup.model` (количество параметров), `setup.dataset` (масштаб) и `setup.max_steps` (сокращённые шаги):

   | Типичный сценарий пилота | Ожидаемая длительность |
   |--------------------------|------------------------|
   | Один GPU + небольшой набор данных (CIFAR / небольшой бенчмарк NLP) | 5 – 30 мин |
   | Один A100 + средний набор данных (ImageNet / GLUE) | 30 мин – 2ч |
   | Multi-GPU или дообучение большой модели (≥7B) | 1 – 4ч


3. **Запуск**:
   ```bash
   screen -dmS pilot-{slug} bash -c \
     "cd $(pwd) && bash experiments/pilot/code/{slug}/run.sh 2>&1 | tee experiments/pilot/code/{slug}/pilot.log"
   ```
   - Уведомите пользователя: "Пилот запущен."

4. **Мониторинг до завершения**:
   Включите **монитор** в терминале для опроса и мониторинга процессов подготовки к эксперименту

#### Удалённый режим (`--env remote`)

**Предусловие**: пользователь настроил `config/server.yaml`.

1. **Проверка доступности**: `python3 tools/remote.py status`
   - Если недоступно → сообщите об ошибке и предложите проверить `config/server.yaml`

2. **Поиск свободного GPU**: `python3 tools/remote.py gpu-status` (пропустите, если `setup.hardware` — `cpu`/`none`/пусто и код не содержит ключевых слов CUDA/GPU)
   - Если нет свободного GPU → сообщите об использовании каждого GPU, предложите подождать или использовать `--env local`

3. **Синхронизация кода**: `python3 tools/remote.py sync-code`
   - Отправляет директорию пилотного кода в удалённый `work_dir`

4. **Оценка времени выполнения** (та же логика оценки, что и для локального режима — см. таблицу выше)
   - Установите интервал опроса пропорционально (та же таблица)

5. **Установка зависимостей** (в первый раз или если изменились требования):
   ```bash
   python3 tools/remote.py setup-env --requirements experiments/pilot/code/{slug}/requirements.txt
   ```

6. **Запуск удалённого пилота**:
   ```bash
   python3 tools/remote.py launch \
     --name "pilot-{slug}" \
     --cmd "bash experiments/pilot/code/{slug}/run.sh" \
     --gpu {gpu_index} \
     --log-file "experiments/pilot/code/{slug}/pilot.log"
   ```
   - Уведомите пользователя: "Пилот запущен (удалённо)."

7. **Мониторинг до завершения**:
   Включите **монитор** в терминале для опроса и мониторинга процессов подготовки к эксперименту

**Этап 3: Сбор и отчёт**

1. **Проверка завершения запуска**: убедитесь, что сессия screen `pilot-{slug}` завершилась. Если всё ещё активна после мониторинга, сообщите и ждите.

2. **Получение удалённых результатов** (только удалённый режим):
   ```bash
   python3 tools/remote.py pull-results \
     --remote-path "experiments/pilot/code/{slug}/results/" \
     --local-path "./experiments/pilot/code/{slug}/results/"

   python3 tools/remote.py pull-results \
     --remote-path "experiments/pilot/code/{slug}/pilot.log" \
     --local-path "./experiments/pilot/code/{slug}/"
   ```
   Если получение не удалось для некоторых файлов → сообщите, какие файлы отсутствуют, продолжите с доступными данными.

3. **Проверка файлов результатов**: `experiments/pilot/code/{slug}/results/seed_*.json`
   - Перечислите доступные файлы результатов
   - Если файлы результатов отсутствуют → сообщите об ошибке "файлы результатов не созданы (возможно, запуск упал)"
   - Если файлы результатов есть, но неполные (частичные сиды) → используйте доступные сиды, отметьте в отчёте

4. **Чтение лога пилота**: `experiments/pilot/code/{slug}/pilot.log`
   - Сканирование на ошибки, предупреждения, OOM, сигналы расхождения
   - Извлечение контекста поведения во времени для финального отчёта
   - Запись любых аномалий, обнаруженных во время мониторинга этапа 2

5. **Парсинг результатов**:
   - Чтение каждого файла результатов (JSON)
   - Вычисление среднего ± стандартное отклонение для каждой метрики (по сидам)
   - Сравнение с `expected_value` базового метода (из спецификации пилота)
   - Вычисление дельты: `пилот_среднее - базовое_ожидаемое`

6. **Вывод PILOT_REPORT в терминал**:
   ```markdown
   # Отчёт о пилоте: {slug}

   ## Результаты
   | Метрика | Базовая | Пилот (среднее±стд) | Δ |
   |---------|---------|---------------------|---|
   | {metric} | {baseline-value} | {mean}±{std} | {delta} |

   ## Детали запуска
   - Завершённые шаги: {max_steps}
   - Время выполнения: {elapsed}
   - Завершённые сиды: {N}/{total}
   - Среда: {local | remote}
   - Лог: experiments/pilot/code/{slug}/pilot.log

   ## Аномалии
   - {список аномалий, обнаруженных во время запуска, или "Нет"}

   ## Следующие шаги
   - Переходите к /exp-pilot-eval для оценки вердикта и обновления wiki
   ```

7. **Возврат** сырых результатов и ключевых метрик вызывающему (например, `/ideate` Этап 5). НЕ изменяйте какие-либо wiki-страницы — пилотные результаты оцениваются через `/exp-pilot-eval`, а не через этот навык.

## Ограничения

- **Не требует wiki-страницы эксперимента**: читает из `experiments/pilot/{slug}.yaml`
- **Не записывает в wiki-страницы**: пилотные результаты возвращаются вызывающему; обновления страницы идеи выполняются через `/exp-pilot-eval`
- **Код хранится в `experiments/pilot/code/{slug}/`**: не записывайте в корень проекта или в другое место
- **Результаты должны быть сохранены**: все пилотные результаты сохраняются как JSON в `experiments/pilot/code/{slug}/results/seed_{N}.json`
- **Многосидовые результаты используют среднее ± стд**: сообщайте среднее ± стд, а не результаты одного запуска
- **Проверка работоспособности должна пройти**: ошибка проверки на этапе 1 блокирует запуск (если пользователь явно не отменяет)
- **Графовые рёбра здесь не создаются**: пилотные эксперименты не создают графовых рёбер
- **Попытки автоматического исправления ограничены 1**: предотвращает бесконечные циклы перезапуска

## Обработка ошибок

- **Спецификация пилота не найдена**: сообщите об ошибке, предложите сначала запустить `/ideate` для генерации спецификации
- **В спецификации пилота отсутствуют поля**: сообщите, какие обязательные поля отсутствуют, предложите повторно запустить `/ideate`
- **GPU недоступен**: сообщите об ошибке, предложите подождать освобождения GPU
- **Проверка работоспособности не прошла**: сообщите подробную ошибку, попробуйте одно автоматическое исправление, если всё ещё не работает — сообщите об ошибке и остановитесь
- **Файлы результатов отсутствуют**: сообщите об ошибке "файлы результатов не созданы (возможно, запуск упал)"
- **Тайм-аут сессии screen**: если сессия screen сохраняется более 2× ожидаемого времени, предупредите пользователя, но не принудительно завершайте
- **Удалённое подключение не удалось**: сообщите об ошибке SSH, предложите проверить конфигурацию подключения и `config/server.yaml`
- **Удалённый GPU недоступен**: сообщите об использовании каждого GPU, предложите подождать или использовать `--env local`
- **Получение удалённых результатов не удалось**: сообщите, какие файлы отсутствуют, продолжите с доступными локальными данными

## Зависимости

### Навыки (через инструмент Skill)
- Нет

### Инструменты (через Bash)
- `nvidia-smi` — статус локального GPU
- `screen` — управление фоновыми процессами локально
- `python3 tools/remote.py <command>` — удалённые операции (status, gpu-status, sync-code, setup-env, launch, check, tail-log, pull-results)

### Конфигурация
- `config/server.yaml` — конфигурация удалённого сервера (требуется только при `--env remote`)

### Claude Code Native
- `Read` — чтение спецификации пилота и wiki-страниц
- `Write` — запись пилотного кода в `experiments/pilot/code/{slug}/`
- `Bash` — выполнение пилотного кода, мониторинг процессов

### Вызывается из
- `/ideate` Этап 5
- Пользователь напрямую
